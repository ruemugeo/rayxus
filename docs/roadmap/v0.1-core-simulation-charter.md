# v0.1 Core Simulation Charter

Status: Draft  
Scope: First implementation milestone after architecture foundation

## Purpose

v0.1 proves Rayxus is an engine, not an app. It must demonstrate headless simulation, deterministic execution, save/load, events, and explanation before world, economy, society, or visualization grows too large.

## Theme

Core simulation loop with inspectable causality.

## Non-Negotiable Outcomes

- Runs headless.
- Uses seeded random streams.
- Accepts commands.
- Advances deterministic simulation time.
- Emits structured events.
- Emits structured explanations for major events.
- Saves and loads through a storage port.
- Replays same scenario with same seed and command sequence.
- Has tests that fail when determinism breaks.

## Explicit Non-Goals

- No React Studio.
- No WebGPU.
- No production database.
- No full economy.
- No full citizens/families model.
- No military.
- No diplomacy.
- No executable plugins.
- No planetary scale.

## Target Scale

Recommended v0.1 target:

- Hundreds to low thousands of entities.
- One scenario.
- One runtime process.
- One active simulation region.
- JSON persistence only.

This scale is intentionally modest. Goal is engine correctness, not spectacle.

## Canonical v0.1 Scenario

Name: `isolated-valley-smoke`

Purpose:

Validate time, state, commands, events, explanations, save/load, and replay.

Scenario shape:

- One region.
- One settlement.
- A small population represented as simple entities or cohorts.
- One food stock.
- One scheduled consumption process.
- One shortage threshold.
- One command that changes available food or population demand.

Expected historical event:

- Food shortage starts when stock falls below threshold.

Required explanation:

- Direct cause: food stock below shortage threshold.
- Affected entities: settlement and population group.
- State deltas: food stock and shortage status.
- Contributing factors: consumption rate and starting stock.

## Minimum Architecture Surface

### Kernel

Must provide:

- Simulation clock.
- Fixed tick advancement.
- Module registration.
- System scheduling.
- Command dispatch.
- Event collection.
- Random stream registry.

### State

Must provide:

- Stable entity IDs.
- Serializable state records.
- State delta output.
- Module-owned state namespaces.

### Commands

Must provide:

- Command envelope.
- Command validation result.
- Command execution result.
- Rejected command event or diagnostic.

### Events

Must provide:

- Event envelope.
- Event type.
- Simulation time.
- Source module.
- Affected entity IDs.
- Optional state delta references.
- Explanation reference or inline explanation.

### Explanation

Must provide:

- Direct cause.
- Affected entities.
- State deltas.
- Contributing factors.

### Save/Load

Must provide:

- JSON snapshot adapter.
- Engine version field.
- Schema version field.
- Scenario ID.
- Seed/random state.
- Module state payloads.

### Replay

Must provide:

- Run scenario from seed.
- Record command sequence.
- Compare emitted event sequence.
- Fail test if event sequence differs.

## Acceptance Tests

Required tests before v0.1 is considered complete:

- Same seed, same commands, same event sequence.
- Save at tick N, load, continue, same event sequence as uninterrupted run.
- Food shortage event includes minimum explanation fields.
- Invalid command is rejected without corrupting state.
- Headless runner completes scenario without UI or storage adapter other than JSON.

## Design Constraints

- No module may import UI or database packages.
- No random calls outside engine random streams.
- No unversioned durable schema.
- No event without source module and simulation time.
- No major event without explanation.
- No state mutation outside system execution.

## v0.1 Exit Criteria

v0.1 is complete when:

- A developer can run the canonical scenario headlessly.
- Output includes deterministic events.
- A save can be produced and loaded.
- Replay validates event sequence.
- Food shortage can answer why it happened.
- Architecture boundaries remain intact.
